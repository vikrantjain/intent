# Distinctions

Four distinctions carry the work. Everything else is judgment. None of it is specific to
software. The same distinctions apply to research, writing, events or a hiring decision.

## Problem vs. solution

A problem says what is wrong now and for whom. A solution says what to do. "Run a survey of our
members" is a solution. "Members are leaving in their first year and nobody knows why" is a
problem.

Naming a solution is fine if the problem behind it is recoverable. If the user cannot state it
when asked, establish it first: the solution was never checked against anything.

A deliberate choice and a first idea read the same on the page. Asking why this approach tells
them apart in one exchange.

## Constraint vs. preference

A constraint holds whoever does the work: a deadline, a regulation, a budget, a system that
already exists and will not change. A preference is the user's taste or habit, and it can bend
if something better shows up.

Users routinely present preferences as constraints without noticing. Every option that conflicts
with one then silently disappears. When a stated constraint has no source outside the user, ask
what happens if it does not hold.

## Stated vs. assumed success

Success is stated when someone other than the author could tell, from the request alone, whether
the result is right. Most requests do not clear that bar. "Make it faster" and "clean this up"
leave the standard in the user's head.

This is the most useful thing to recover, because later work is checked against it.

## Room left for the agent

A brief either invites the agent's judgment or forecloses it. Foreclosing is fine when the user
has decided and wants execution. It goes wrong when it is accidental: the user would have
welcomed a better approach and never signalled it.

The test is whether following the request exactly leaves any point where the agent could propose
something different.
